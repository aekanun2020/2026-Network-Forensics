# คำตอบอ้างอิงที่ตรวจจากหลักฐาน — 10.70.0.66

[โจทย์](QUESTION.md) · [คำตอบ agent เดิม](AGENT-ANSWER.md) · [ผลตรวจและวิธีทำซ้ำ](verification/README.md) · [หลักฐาน](evidence/README.md)

เรียบเรียงและประเมินโดย **Codex วันที่ 8 กันยายน 2026** จากหลักฐานหกไฟล์และการอ่านไฟล์โดยตรง ไม่ใช้ external LLM judge คำตอบนี้เพิ่มเติมข้อจำกัดและผลอ่าน body เต็มจาก cross-check โดยไม่แก้คำตอบ agent เดิมย้อนหลัง

## ข้อสรุปที่ยืนยันได้

**10.70.0.66 ติดต่อคู่สื่อสาร 27 IP ใน 265 conversations และมี packets เกี่ยวข้อง 1,255 packets** เรียงเป็นการสอบถาม DNS → ส่งข้อมูลไปยัง IP ที่ได้จาก DNS → ติดต่อเครื่องภายใน 25 เครื่อง โดย 265 conversations ประกอบด้วย DNS exchanges บน UDP 120 ชุด และ TCP conversations 145 ชุด ไม่ใช่ TCP connections 265 ชุด

ยืนยันว่ามีการรับส่งข้อมูลตามรายละเอียดด้านล่างได้ แต่ **ไม่ยืนยันการควบคุมเครื่องด้วย C2 การขโมยไฟล์จริง หรือการยึดเครื่องภายในสำเร็จ** ชุดหลักฐานทั้งหมดมาจาก PCAP สังเคราะห์เดียวกันตาม source_relationship ใน [manifest](evidence/source-manifest.json) จึงไม่ใช่การยืนยันจากเซนเซอร์อิสระห้าแหล่ง

## การส่งข้อมูลไป 203.0.113.66

ตรวจ request payload **ครบทั้ง 120 bodies** พบ `POST /upload/0 HTTP/1.0` ถึง `POST /upload/119 HTTP/1.0`, `Host: exfil.evidence.example.test` และ `Content-Length: 50000` ทุก request มี body 50,000 bytes จริง P #244 เป็น request แรก, #1077 เป็น request สุดท้าย และ requests ระหว่างนั้นอยู่ทุก 7 packets

| สิ่งที่นับ | รวม | หลักฐาน |
|---|---:|---|
| TCP payload ขาออก รวม request line/headers/body | 6,010,330 bytes | P request payloads; C.orig_bytes / N.bytes / F.sentbyte #121–240 |
| HTTP bodies | 6,000,000 bytes | 120 × 50,000; [http_requests](verification/current/measurements.json) |
| Request line, headers และตัวคั่นก่อน body | 10,330 bytes | ผลต่างและการอ่าน header ครบทุก request |
| TCP payload ขากลับ | 240 bytes | `OK` 2 bytes × 120; P #245 ถึง #1078 ทุก 7 packets; C.resp_bytes / F.rcvdbyte #121–240 |

ยอด 6,010,330 เป็น **TCP payload bytes** ของช่วงอัปโหลด ไม่ใช่ขนาด PCAP หรือ bytes บนสายที่รวมทุก protocol header ป้าย HTTPS ใน F ไม่ตรงกับ payload ข้อความล้วนที่อ่านได้ จึงใช้ผลอ่าน payload อธิบาย traffic ช่วงนี้

แต่ละ body มีอักขระชนิดเดียวซ้ำ 50,000 ตัว วน A ถึง T ตามหมายเลข request แล้วเริ่มซ้ำ ครบ 120 requests ไม่ได้ตรวจเพียงส่วนต้นเหมือนขอบเขตในคำตอบ agent เดิม ผลนี้รองรับลักษณะข้อมูลทดสอบในชุดสังเคราะห์ ไม่ระบุว่ามีไฟล์ลับใดถูกขโมย ส่วนข้อมูลตอบกลับ `OK` ยืนยันการตอบกลับ 2 bytes ต่อครั้ง แต่ไม่พิสูจน์ว่าปลายทางบันทึกข้อมูลลงดิสก์หรือประมวลผลสำเร็จ และไม่ใช่ HTTP status line ที่จะนำไปอ้างเป็นสถานะสำเร็จของ HTTP

## การติดต่อเครื่องภายใน

ทุก IP ในตารางมี prefix `10.70.1.` โดยตัวที่ n เชื่อมกับ C/N/F record #240+n

| พอร์ต TCP | เลขท้าย IP ปลายทาง | จำนวน |
|---|---|---:|
| 22 | 1, 4, 7, 10, 13, 16, 19, 22, 25 | 9 |
| 445 | 2, 5, 8, 11, 14, 17, 20, 23 | 8 |
| 3389 | 3, 6, 9, 12, 15, 18, 21, 24 | 8 |

ตรวจทั้ง 25 คู่พบ `LAB13 coherent remote service probe` ยาว **35 bytes** ส่งจาก 10.70.0.66 และรับ `OK` **2 bytes** ทุกปลายทาง รวมขาออก 875 bytes ขากลับ 50 bytes คู่แรกอยู่ P #1084–1085 และคู่สุดท้าย #1252–1253; สำหรับเครื่องที่ n payload ขาออกอยู่ #1084+7(n−1) และขากลับอยู่ packet ถัดไป ดู [lateral_payloads](verification/current/measurements.json)

C #241–265 ระบุ conn_state=SF และ P แสดงการแลกเปลี่ยนข้อมูลจริง แต่ไม่พบ payload ที่พิสูจน์การยืนยันตัวตน การเปิด remote session การเข้าถึงไฟล์ หรือการรันคำสั่งสำเร็จ จึงยังเรียกไม่ได้ว่าเข้าสู่ระบบ SSH/SMB/RDP หรือยึดเครื่องได้จากหมายเลขพอร์ตและป้ายใน F เพียงอย่างเดียว

## การเชื่อม records และข้อมูลขากลับ

| การเชื่อม | ผลและตำแหน่ง |
|---|---|
| D → C ด้วย uid, tuple และเวลา | D #1–120 → C #1–120 แบบหนึ่งต่อหนึ่ง เวลาเท่ากัน |
| C → N ด้วย IPs/ports/protocol และเวลา | #1–265 ตรงกันหนึ่งต่อหนึ่ง; timestamps ต่างประมาณ 1–6 ms และ outbound bytes/packets ตรงกัน |
| C → F ด้วย uid ↔ parentuid และ tuple | #1–265 ตรงกันหนึ่งต่อหนึ่ง; bytes ทั้งสองทิศทางตรงกัน; F ระบุ simulation=true และ evidence_origin=pcap-derived |
| S → C และ P ด้วย tuple/time/pcap_count | S #1–120 เป็น DNS, #121–240 เป็นการส่งออก, #241–340 เป็นการติดต่อภายใน; 340 alerts ครอบคลุม 265 conversations |

alerts ภายใน **100 รายการมาจาก 25 conversations โดยมี 4 alerts ต่อ conversation** ไม่ใช่การเชื่อมต่อภายใน 100 ครั้ง ไม่พบ unmatched ในการเชื่อม records ของเป้าหมายที่ตรวจตาม fields ข้างต้น และไม่พบความขัดกันระหว่าง 265 PCAP conversations กับ byte/packet/time fields ของ C ที่ตัวตรวจเทียบ ดู `joins`, `join_errors` และ `pcap.packet_log_disagreements` ใน [ผลวัด](verification/current/measurements.json)

N ไม่มี record ที่ destination_ip เป็น 10.70.0.66 ภายในไฟล์นี้ แต่ PCAP และ C/F ยืนยัน response payload จึง **ห้ามสรุปว่าไม่มี traffic ขากลับจากการไม่มี reverse NetFlow row** เช่นเดียวกัน C ไม่มี record ที่เครื่องอื่นเป็น originator มายังเป้าหมายในไฟล์นี้ ไม่ได้พิสูจน์ว่าไม่เคยเกิดขึ้นนอกขอบเขตข้อมูล

## ข้อสงสัยและสิ่งที่ยังยืนยันไม่ได้

| ข้อสงสัยที่ตรวจต่อได้ | สิ่งที่ข้อมูลรองรับ | สิ่งที่ยังขาด |
|---|---|---|
| DNS beaconing / C2 | DNS 120 ครั้งเป็นคาบ 60 วินาที และมี IP คำตอบสัมพันธ์กับปลายทางอัปโหลด | คำสั่ง C2, malware/process หรือหลักฐานควบคุมเครื่อง |
| การนำข้อมูลออกโดยมิชอบ | POST ต่อเนื่อง 120 ครั้ง พร้อมปริมาณและทิศทางชัดเจน | ไฟล์ต้นทาง ข้อมูลลับ เจ้าของข้อมูล และข้อเท็จจริงเรื่องการอนุญาต |
| การสำรวจหรือเตรียม lateral movement | fan-out ไป 25 IP ภายในและแลกเปลี่ยนข้อความ probe | authentication, remote execution หรือการยึดเครื่องสำเร็จ |

คำว่า C2, Outbound Transfer และ Remote Service ใน alert เป็นป้ายกฎในชุดข้อมูล ไม่ได้ยืนยันผลโจมตี ยังไม่ทราบผู้ใช้ กระบวนการ ต้นทางการติดเชื้อ หรือผู้ควบคุมปลายทางจากหลักฐานหกไฟล์นี้ และการตรงกันของหลาย views ที่สร้างจาก parent เดียวต้องไม่ถูกนับเป็นพยานอิสระหลายแหล่ง
