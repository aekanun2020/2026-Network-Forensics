ผลนับ DNS และการติดต่อทั้งหมดตรวจสอบได้จาก [ผล MCP ของ DNS](support/mcp/dns-summary.json) และ [ผล MCP ของ Zeek conn](support/mcp/conn-summary.json)

การส่งออกไป `203.0.113.66` มีรายละเอียดที่ยืนยันได้ดังนี้:

- พบ **HTTP ข้อความล้วนบน TCP/443**: `POST /upload/0` ถึง `/upload/119`, `Host: exfil.evidence.example.test` และ `Content-Length: 50000` ครบ 120 requests ดังนั้นป้าย `HTTPS` ใน F ไม่ตรงกับ payload ที่สังเกตได้
- รวม TCP payload ขาออก **6,010,330 bytes** แบ่งเป็น HTTP body **6,000,000 bytes** และ request line/headers **10,330 bytes** ยอดตรงกับ `orig_bytes` ใน C, `bytes` ใน N และ `sentbyte` ใน F
- C และ F บันทึก payload ขากลับรวม **240 bytes**; P #245 และ #1078 แสดงคำตอบ `OK` ยาว 2 bytes สำหรับการส่งครั้งแรกและสุดท้าย คำตอบนี้ยืนยันว่ามีข้อมูลตอบกลับ แต่ไม่พิสูจน์ว่าปลายทางบันทึกข้อมูลลงดิสก์สำเร็จ
- ส่วนต้นของ body ที่อ่านพบอักขระซ้ำ เช่น `AAAA…` และ `TTTT…` **ยังระบุไม่ได้ว่าเป็นไฟล์ใดหรือข้อมูลลับอะไร** เพราะตรวจเนื้อหาเพียงส่วนต้นของแต่ละ payload

ดู [การส่งครั้งแรกพร้อมข้อมูลตอบกลับ](support/mcp/pcap-upload.json) และผลตรวจ requests ครบ 120 ครั้ง: [ชุด 1](support/mcp/upload-0.json), [ชุด 2](support/mcp/upload-1.json), [ชุด 3](support/mcp/upload-2.json)

การติดต่อเครื่องภายในแบ่งได้ดังนี้ ทุก IP ในตารางมี prefix `10.70.1.`:

ตรวจ payload ครบทั้ง 25 คู่ พบข้อความ **`LAB13 coherent remote service probe` ยาว 35 bytes** จาก 10.70.0.66 และคำตอบ **`OK` ยาว 2 bytes** จากทุกปลายทาง รวมส่ง 875 bytes รับ 50 bytes ส่วน C บันทึก `conn_state=SF` ทั้งหมด หลักฐานนี้ยืนยันการเชื่อมต่อและแลกเปลี่ยนข้อความ แต่ **ไม่ได้แสดงการยืนยันตัวตน การเปิด remote session การเข้าถึงไฟล์ หรือการรันคำสั่งสำเร็จ** แม้ F จะติดป้าย SSH/SMB/RDP ก็ตาม ([packets ของทั้ง 25 คู่](support/mcp/lateral-payloads.json))

การเชื่อมหลักฐานช่วยป้องกันการนับซ้ำ:

- D เชื่อม C ด้วย `uid` ได้ **120 คู่ เวลาเท่ากัน**
- C เชื่อม N ด้วย source/destination IP, source/destination port, protocol และเวลา ได้ **265 คู่แบบหนึ่งต่อหนึ่ง** เวลาต่างกันประมาณ 1–6 มิลลิวินาที
- C เชื่อม F ด้วย `uid ↔ parentuid` ได้ **265 คู่**; F ระบุ `simulation=true`, `evidence_origin=pcap-derived` จึงไม่ควรนับเป็นการยืนยันอิสระจากอุปกรณ์จริง
- S ทั้ง **340 alerts** เชื่อมกลับได้กับ C **265 การติดต่อ**: DNS 120, ส่งออก 120 และภายใน 100 alerts จาก 25 การติดต่อ—**4 alerts ต่อการติดต่อภายใน** จึงไม่ใช่การเชื่อมต่อภายใน 100 ครั้ง ([ผลเชื่อม C–S](support/mcp/join-conn-ids.json))

**ข้อสงสัยที่มีหลักฐานรองรับ แต่ยังไม่ใช่ข้อยืนยัน** คือ DNS ที่เกิดเป็นคาบอาจเข้าลักษณะ beaconing; การอัปโหลดต่อเนื่องอาจเป็นการนำข้อมูลออกโดยมิชอบ; และการไล่ติดต่อเครื่องภายในอาจเป็นการสำรวจหรือเตรียมเคลื่อนย้ายไปยังเครื่องอื่น อย่างไรก็ตาม ชื่อ `C2`, `Outbound Transfer` หรือ `Remote Service` ใน alerts เป็นชื่อกฎ ไม่ใช่หลักฐานว่ามัลแวร์ทำงานหรือโจมตีสำเร็จ

อีกข้อจำกัดสำคัญ: N ไม่พบ record ที่มีปลายทางเป็น 10.70.0.66 **ไม่ได้แปลว่าไม่มีข้อมูลขากลับ** เพราะ PCAP และ C แสดงคำตอบกลับชัดเจน ส่วน C ไม่พบการติดต่อที่เครื่องอื่นเป็นผู้เริ่มมายัง 10.70.0.66 ภายในไฟล์นี้ ยังไม่ทราบผู้ใช้ กระบวนการ ต้นทางการติดเชื้อ หรือเจ้าของปลายทางจากหลักฐานทั้งหกไฟล์นี้
